Git→main Merger Utility (merge.mjs)

Domain: Git Automation, Multi-Worktree and Single-Checkout Workflows & Step-Based Releases

Overview

The /merge command provides a zero-token, local utility to automate the validation and integration of a completed Step 5 feature branch (or a specific stable commit) into the main branch. It ensures compliance with the Princess-Pi 5-Step Development Flow without invoking costly LLM reasoning turns.

CLI Mode (Outside Pi Coding Agent) — Cross-Harness

bin/merge.mjs is a standalone port of the same validation/merge/push sequence (plain execSync git calls, no Pi dependency). It ships as plain ESM JavaScript (#!/usr/bin/env node) rather than TypeScript: installed globally for Claude Code (npm install -g github:duppypro/princess-pi-packages) the bin lives under node_modules/, where Node refuses --experimental-strip-types (ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING), so the shipped file must need no type stripping at runtime. It is generated, not handwritten: bin/merge.mjs carries a ⚠️ GENERATED by build.ts from bin/merge.ts — DO NOT EDIT banner and is produced by bun run build. Edit bin/merge.ts. (This paragraph previously said the file "needs no build step" — true before the bun build migration, false since.) Invoke it as the npm-global merge [commit-ish], via the ./merge wrapper from the repo root, or through Claude Code's ! prefix (e.g. !merge 638e9b4) — Claude has no extension-dispatch that bypasses the model the way Pi's registerCommand does, so the CLI is how it stays zero-token there. Behavior matches the Pi extension; only the output channel differs (console.log instead of ctx.ui.notify). The typed twin extensions/merge.ts remains the Pi-runtime version.

Worktree vs single-checkout: if a dedicated main git-worktree exists, the merge runs there and never disturbs the feature checkout (Pi's original multi-worktree design). Otherwise — the common Claude Code case — it falls back to an in-place single-checkout merge in the current repo, always returning you to your feature branch afterward and rolling back (git merge --abort) on conflict.

Verification Rules

Before any merge operations occur, the extension strictly enforces the following rules in sequence:

  1. No Self-Merge: Rejects running the command if the active worktree is already on the main branch.
  2. Clean Feature Worktree: Verifies that the current feature worktree contains no uncommitted (staged or unstaged) modifications.
  3. In Sync with Origin: Fetches origin and ensures the targeted commit-ish is present in the history of the remote tracking branch (preventing unpushed commits).
  4. Step 5 Validation: Validates the targeted commit's subject line only against a word rule, not a leading phrase (isStep5ApprovedMessage, since #100): some occurrence of approved must have both code and a spec-word (spec/specs/specification/specifications) before it, and no not anywhere before it. Case-insensitive, whole words, free word order — so docs: Code and Spec Approved — … (#158) and Specs and code approved, ship it both pass. Subject-only on purpose: Step 4 commit bodies routinely mention specs and would false-positive. If it does not match, the command fails and automatically suggests the most recent historical commit that does. (This previously documented the pre-#100 regex /^Code and Spec Approved(\s*\([^)]*\))?\s*:/, which required the phrase to lead and rejected legitimate Step 5 commits over word order.)
  5. Clean Target (when a main worktree exists): If a dedicated main worktree is found, verifies it contains no uncommitted changes. In single-checkout mode this step is skipped — the current feature worktree was already verified clean above, and the tool switches branches in place.

Merge and Push Execution

Once all validations pass, the utility integrates and pushes automatically. Two paths:

Multi-worktree path — inside the dedicated main worktree directory:

  1. Switches/ensures the main worktree is on the main branch.
  2. Pulls the latest updates from origin/main (--ff-only).
  3. Merges the validated target commit into main (leaving any subsequent unapproved commits on the feature branch).
  4. Rebuilds tracked artifacts and commits any delta (#177) — see below.
  5. Pushes the newly merged main branch to origin.
  6. Logs success; the active feature worktree was never touched by the merge itself.

Single-checkout fallback — in the current repo, wrapped so it always returns you to the feature branch:

  1. Checks out main in place (creating it from origin/main if the local branch is absent) and pulls --ff-only.
  2. Merges the validated target commit into main.
  3. Rebuilds tracked artifacts and commits any delta (#177) — see below.
  4. Pushes main to origin.
  5. On a merge failure, runs git merge --abort and reports an LLM-actionable error; a finally step always checks the feature branch back out, so you are never stranded on main or mid-merge. A build failure is deliberately excluded from that handler — the merge succeeded and nothing is rolled back, so it surfaces under its own banner instead.

Post-Merge Artifact Rebuild (#177)

This repo tracks generated bin/*.mjs on purpose (required for npm install -g from a git URL). Two branches touching different bundled sources each commit an artifact that is correct for their own tree; the merge of the two produces output neither branch committed, so main lands stale with a clean git status. Git's 3-way merge cannot catch this, because a bundle's derived parts — module counts, tables of contents, ordering, identifier numbering — are not a line-wise function of the sources.

After merging and before pushing, merge runs bun run build and commits any delta as a separate build: regenerate tracked artifacts after merging <hash> commit. Before-the-push is deliberate: building afterwards would need a second push and would leave a window where origin/main is stale. A separate commit rather than an amend keeps "what the merge did" and "what the build did" independently auditable.

It stays generic. A build runs only where there is one: a package.json with a build script, and bun on PATH. Absent either, merge says so and continues — a repo with no build has nothing to regenerate. No delta means no commit. --no-build opts out.

A failing build blocks the push. The merge commit exists locally, so nothing is lost, and pushing a tree that does not build is worse than a manual recovery. This reports as ❌ Merge not pushed:, never ❌ Merge Aborted: — the merge landed, and a banner must name what actually failed.

Branch Cleanup (--cleanup, #143)

Cleanup runs after a successful merge and push, and is worktree-aware. In a single checkout it switches you to main and deletes the feature branch. In the worktree layout it cannot — git refuses to check out a branch already checked out elsewhere, so the old unconditional git checkout main could never succeed there. Instead it runs git checkout --detach main in the feature worktree: a detached HEAD does not claim the branch, which frees git branch -d.

Local before remote. The local branch is deleted first, and only then the remote. The old order deleted the remote first, so a local failure stranded you at remote-gone/local-present — the state that later makes git branch -d complain about an upstream that no longer exists. The current order fails to remote-present/local-gone, which is inert and re-runnable.

Cleanup can never fail the merge. It is best-effort by construction: any failure reports as a cleanup failure that states the merge succeeded and needs no undoing. Deletion uses -d, not -D — the ancestor check has already proved the branch is in origin/main, so force would only hide the case where that check was wrong.

The worktree itself is left in place. Removing it is a manual step by standard (a worktree may be an assigned scope for a parallel agent session), so cleanup prints the git worktree remove command rather than running it.

Config files live at ~/.config/princess-pi/merge.json (user-global) and ./.princess-pi/merge.json (project-local, overrides global). CLI flags take highest precedence.
